# Avatar Repo Blueprint

This blueprint defines a reusable openLifeOS / digital-avatar repository structure.

Generated repos can be Chinese or English. Default to the Chinese template (`zh-CN`); use the English template (`en-US`) only when the user requests it or the target avatar primarily operates in English.

## Factory Contract

The current `openLifeOS` repo is a factory. It owns the factory Skill protocol, avatar templates, scripts, references, and validation gates. Concrete generated avatars should be created under the local output area:

```text
openLifeOS/
└── output/
    └── meta/
        └── Target.LifeOS/
```

`output/meta/` is local factory output. Generated repo contents are ignored by git by default; commit templates and scripts, not private generated instances.

## Generated Repo Contract

Generated repos should conform to `schemas/lifeos.schema.v2.yml`.

v2 top-level directories are limited to:

- lifecycle layers: `identity/`, `metabolism/`, `runtime/`, `work/`, `evolution/`, `capabilities/`, `identities/`.
- governance layers: `artifacts/`, `integrations/`, `security/`, `docs/`.
- compatibility layer: `legacy/`.

Historical v1/v1.5 top-level directories such as `agents/`, `apps/`, `profiles/`, `scripts/`, `design/`, `life/`, `system/`, `skills/`, `memory/`, `cognition/`, `intake/`, and `roles/` must be migrated with `scripts/migrate_lifeos_schema.py` or preserved under `legacy/` if they cannot be classified.

Every generated avatar repo should have:

```text
output/meta/Target.LifeOS/
├── replicateme.yml
├── LIFEOS-CATALOG.html
├── AGENT.md
├── matrix.yml
├── artifacts/
├── identity/
│   ├── cognition/
│   └── memories/
├── metabolism/
│   ├── inbox/
│   ├── processing/
│   └── extracted/
├── runtime/
│   ├── sessions/
│   ├── runtime-skills/
│   ├── runtime-lessons/
│   └── memory/
├── evolution/
│   ├── ipo/
│   └── organ-systems/
├── capabilities/
├── identities/
├── work/
├── integrations/
│   └── agents/openai.yaml
├── security/
├── legacy/
└── docs/
    └── evidence-sufficiency.md
    └── self-evolution-output-standards.md
```

The root `AGENT.md` is the agent entrypoint. It is not an installable Codex Skill; it should answer:

- What avatar is this?
- Which source should an AI read first for identity, work context, skill execution, or security?
- How should an AI enter real Skills under `evolution/organ-systems/*/SKILL.md` or `capabilities/*/SKILL.md`?
- How should an AI judge structure readiness, content maturity, owner alignment, evidence maturity, and lifecycle stage?
- What should never be invented?
- What material is public, private, linked, or generated?

`matrix.yml` is the machine-readable index. It should mirror the repo structure and list submodules, artifacts, generated outputs, and visibility where known.

`replicateme.yml` is the setup manifest generated from the user's prompt. It records repo language, visibility, GitHub owner, whether `gh` is required, the memory wiki repo, and seed domains for skill recommendations.

`agents/openai.yaml` is the UI metadata for Codex skill chips.

`docs/evidence-sufficiency.md` is required. It separates structure readiness from content maturity and prevents agents from treating a green progress gate as a completed LifeOS. It records maturity level, available evidence, failed/unavailable sources, incomplete areas, and whether candidate Skills are instance-local or installable.

`docs/self-evolution-output-standards.md` is required. It defines the minimum pass/fail fields for Wenxin, PSP, Soul, Design, and IPO Reverse artifacts. If the available material cannot fill the key fields, the artifact must declare `evidence_sufficiency: insufficient` and list targeted missing-information prompts.

The generated repo has two independent status axes:

- Scaffold/progress completion: deterministic files, protocol, permissions, and entrypoints.
- Digital-life lifecycle: Stage 0-8 maturity and age, driven by intake, sessions, lessons, IPO evolution, and capabilities.

Doctor reports must include both axes. A `100%` progress score means structure/protocol readiness only; it is not content maturity, personality maturity, capability maturity, or Stage 8.

Canonical lifecycle data flow:

```text
metabolism/inbox
-> runtime/sessions
-> runtime/runtime-skills
-> runtime/runtime-lessons
-> evolution/ipo
-> capabilities
```

## Layer Contracts

`identity/` answers "who is represented?"

- `public-profile/`: confirmed public facts and external account references.
- `wenxin/`: self-discovery and public positioning generated by Wenxin or an equivalent process. This layer should help the owner understand who they are, where they stand, how complete they are in their field, what gaps remain, where they may go next, and which strong capabilities should become Skills.
- `psp/<person_id>/`: PSP/person model, behavior boundaries, evidence summaries, and validation artifacts.
- `psp/<person_id>/update-log.md`: chronological PSP updates. PSP should evolve as new approved material arrives; raw evidence stays outside the repo.

`metabolism/` answers "what authorized material entered the LifeOS, and how is it digested?"

- `metabolism/inbox/`: raw authorized source manifests, consent boundaries, and material-purpose mapping.
- `metabolism/processing/`: extraction jobs, normalization state, and review queues.
- `metabolism/extracted/`: owner-approved derived evidence packets ready for Wenxin, PSP, runtime, work, or memory routing.
- Do not treat raw metabolism input as stable memory or personality. It must be triaged into sessions, identity evidence, work evidence, memory pointers, or archive.

`runtime/` answers "what actually happened while this LifeOS was working?"

- `runtime/sessions/`: canonical source of life activity. Store session summaries, task context, decisions, feedback, failures, and verification notes.
- `runtime/runtime-skills/`: concrete execution patterns observed or used during sessions.
- `runtime/runtime-lessons/`: candidate lessons from runs. These are not durable truths until reviewed.
- Runtime activity is the primary evidence source for growth; static profile files do not prove the LifeOS is alive.

`evolution/` answers "how does evidence become a stronger person model or method?"

- `evolution/ipo/`: IPO Reverse records that reconstruct inputs, process, outputs, hidden cognition, and reusable patterns from completed work.
- Evolution may update Wenxin, PSP, Soul, Design, memory index, skill recommendations, and capability maps only from approved evidence.
- Runtime lessons can promote only after IPO Reverse plus owner alignment.

`capabilities/` answers "what can this LifeOS reliably do now?"

- Store reviewed capability maps, capability cards, accepted Skill bindings, and installable Skill migration notes.
- Separate instance-local candidate capability from globally discoverable/installable Skill.
- A capability is mature only when it has evidence, scope, limits, acceptance criteria, and current binding paths.

`identities/` answers "which social identity projection is active?"

- Record founder, teacher, author, speaker, operator, or other identity-projection goals, constraints, voice boundaries, authority, accounts, and collaboration mode.
- Identity projections should read from identity/capabilities/work, not duplicate raw evidence.

`work/` answers "where does this LifeOS produce outcomes?"

- Index projects, operating domains, deliverables, work logs, and external systems.
- Work artifacts feed `runtime/sessions/` and `evolution/ipo/`; they are not automatically long-term memory.

`identity/cognition/` answers "what worldview and object contract controls writes?"

- Store taxonomy, ontology, data contracts, and skill-to-data bindings.
- Cognition is part of identity because these contracts describe how the digital person classifies the world, not a separate OS layer.

`identity/memories/`, `runtime/memory/`, and `capabilities/*/memory/` replace the old top-level `memory/` bucket.

- `identity/memories/`: long-term self cognition, stable facts, configured memory wiki entrypoints, and public-safe derived indexes.
- `runtime/memory/`: session-local context, working lessons, and temporary observations.
- `capabilities/*/memory/`: capability-local evidence libraries, examples, acceptance criteria, and reviewed patterns.
- Follow `references/memory-isolation-model.md`: public memory is a derived surface, private memory is the collaboration surface, and raw sensitive material stays in the authoritative private source.

`evolution/organ-systems/` is the home for capability production systems.

- Wenxin, PSP, IPO Reverse, and alignment systems belong here.
- They are not durable user capabilities. They produce or revise identity, runtime lessons, IPO records, and promoted capabilities.

Follow `references/skill-taxonomy-and-promotion.md`: runtime skills produce evidence; durable capabilities absorb only reviewed, recurring, privacy-safe patterns. Runtime skills can upgrade into meta behavior only through IPO Reverse plus alignment review.

`integrations/` answers "which external systems may this avatar use?"

- `github.yml`: GitHub owner, auth method, scopes/permissions, repo creation intent, and token policy.
- `feishu.yml`: Feishu/Lark tenant label, app type, auth method, read scopes, source usage, and token policy.
- `hermes.yml`: self-evolution sync intent. Hermes can summarize new evidence and drive updates to Wenxin, PSP, skill recommendations, memory index, and GitHub PRs without storing secrets.
- Never store app secrets, access tokens, refresh tokens, cookies, or private keys.

`security/` answers "what must not enter this repo?"

- Secrets, passwords, keys, private transcripts, customer details, contracts, financial data, personal IDs, and raw private wiki content are banned.
- Public repos should only contain public facts and abstracted conclusions.
- `security/permissions.yml` summarizes connector permission boundaries and secret storage policy.

`docs/` answers "what should humans see?"

- Optional public visuals, diagrams, or cover assets.
- Generated README narrative belongs to the target repo only if the user wants a public GitHub-facing page.

## Source Mapping

Use this mapping when converting raw input into repo outputs:

| Source type | Destination | Rule |
| --- | --- | --- |
| Confirmed public facts | `identity/public-profile/profile.yml` | Write directly after user confirmation. |
| Resume, intro, website, public posts | `identity/wenxin/` | Generate Wenxin self-discovery and public positioning. |
| Wenxin output | `identity/wenxin/skill-recommendations.yml` | Recommend which personal Skills should be distilled next and what evidence is needed. |
| Interviews, meetings, long notes | `identity/psp/<person_id>/` | Distill into abstract PSP conclusions; do not copy raw material. |
| New approved PSP evidence | `identity/psp/<person_id>/update-log.md` | Record PSP updates and confidence; do not store raw evidence. |
| Private second brain | `identity/memories/` and `identity/memories/wiki-repo.yml` | Configure visibility, authority, public mirror policy, and collaboration mode; link or summarize entrypoints only. |
| Daily Skill lessons | Private memory wiki or private Skill lesson queue | Store raw lesson events privately; promote only public-safe, reusable rules into Skill references. |
| Large PDFs and source artifacts | Private object store, local vault, server path, or private wiki pointer | Keep raw files out of public repos; store metadata, hash, extraction state, and approved abstracts. |
| Thought fragments | `metabolism/inbox/` or private memory intake queue | Capture first, then triage; do not treat unprocessed thoughts as stable public memory. |
| GitHub access choices | `integrations/github.yml` and `security/permissions.yml` | Record auth method and scopes; do not store tokens. |
| Feishu/Lark access choices | `integrations/feishu.yml` and `security/permissions.yml` | Record app type, auth method, read permissions, and source usage; do not store secrets. |
| Hermes update loop | `integrations/hermes.yml` | Record update cadence, source usage, and target artifacts for Wenxin/PSP/Skill evolution. |
| Existing stable capabilities | `capabilities/` and `matrix.yml` | Add as documented capability bindings or migration notes. |
| Security constraints | `security/README.md` | Hardcode early and enforce throughout. |
